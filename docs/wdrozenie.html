System rozliczeń partnerskich

Kompletna instrukcja uruchomienia: od pustego serwera Coolify do działających dashboardów, które co miesiąc same się aktualizują po odebraniu maila z rozliczeniem. Kroki wykonuj po kolei — każdy kończy się weryfikacją, której wynik warunkuje następny.

00

Co budujemy i dlaczego tak

Raz w miesiącu przychodzi mail z jednym załącznikiem Excel. Plik ma pięć arkuszy, dwa oddzielne rozliczenia (kanał główny i Amazon przez MJ), około 300 pozycji sprzedaży i 1100 pozycji magazynowych. System ma to odebrać, sprawdzić, zapisać i pokazać — bez ręcznej pracy i bez ryzyka policzenia tego samego dwa razy.

Pięć decyzji projektowych, które warto znać

Trzy warstwy w bazie

Surowy zrzut arkuszy w JSONB zostaje na zawsze. Jeśli parser kiedyś źle zinterpretuje kolumnę, dane przeliczysz bez proszenia nadawcy o pliki.

Idempotencja na trzech poziomach

SHA-256 pliku jako klucz unikalny, klucz naturalny okresu w bazie, transakcyjne DELETE + INSERT pozycji.

Korekty tworzą rewizje

Poprawiony plik za ten sam miesiąc nie nadpisuje danych — powstaje rewizja 2, stara zostaje w audycie.

Kwoty są sprawdzane

Sześć równań rozliczenia przeliczanych niezależnie po każdym załadowaniu. Różnica powyżej grosza to alert.

Przetwarzanie w tle

Worker odpowiada n8n natychmiast i pracuje dalej. Limit 100 s na proxy Cloudflare przestaje mieć znaczenie.

Arkusze opcjonalne

Wymagane są tylko Karta i Raport. Brak arkusza Stok lub Karta_MJ daje ostrzeżenie, nie błąd — starsze rozliczenia nie mają magazynu.

Stan weryfikacji

Cały łańcuch — schemat, ładowanie, wszystkie modele i 29 zapytań dashboardowych — został uruchomiony na PostgreSQL 16 na dwóch prawdziwych rozliczeniach: 2026-06 i 2026-07. Kwoty w bazie zgadzają się z plikami co do grosza (63 869,88 i 60 041,44 zł do zapłaty w kanale głównym; 1 479,22 i 1 485,61 zł w kanale MJ), wszystkie 12 kontroli arytmetyki przeszło, a trendy miesiąc do miesiąca liczą się poprawnie. 16 z 16 testów parsera zdanych.

01

Umieść kod w repozytorium GitHub

Rozpakuj dostarczone archiwum i wypchnij je do prywatnego repozytorium. Coolify będzie z niego budował obraz workera przy każdym wdrożeniu. Archiwum rozpakowuje się do katalogu settlements — możesz go swobodnie przemianować.

terminal · lokalnie
unzip rozliczenia-system.zip
mv settlements rozliczenia && cd rozliczenia

git init
git add .
git status                 # sprawdź listę PRZED commitem
git commit -m "System rozliczeń partnerskich"

git remote add origin git@github.com:ORGANIZACJA/nazwa-repo.git
git branch -M main
git push -u origin main
Zanim wypchniesz

Na liście git status nie może być pliku .env — jest w .gitignore, ale sprawdź. Katalog sample/ zawiera prawdziwe dane finansowe, więc repozytorium musi być prywatne. Jeśli wolisz go nie trzymać w git, usuń go teraz: git rm -r --cached sample/ — testy pominą się same, gdy pliku nie ma.

04

Domeny: Cloudflare i Coolify

Kolejność ma tu znaczenie krytyczne. Najpierw kierujemy DNS bez proxy, żeby Coolify mógł wystawić certyfikat Let's Encrypt, a dopiero potem — jeśli chcesz — włączamy proxy Cloudflare. Odwrotna kolejność to najczęstsza przyczyna wielogodzinnej walki z SSL.

4.1 Ustal adres IP serwera

W Coolify: Servers → Twój serwer, pole IP Address. Albo z terminala serwera:

terminal · na serwerze
curl -4 ifconfig.me

4.2 Cloudflare — dodaj rekordy DNS

Panel Cloudflare → wybierz domenę → DNS → Records → Add record. Dodaj dwa rekordy typu A:

TypeNameIPv4 addressProxy statusTTL
AbiIP serweraDNS only szara chmurkaAuto
ArozliczeniaIP serweraDNS only szara chmurkaAuto
Proxy na tym etapie musi być wyłączone

Kliknij pomarańczową chmurkę, aż zrobi się szara („DNS only”). Coolify weryfikuje domenę metodą HTTP-01 — Let's Encrypt musi trafić bezpośrednio na Twój serwer. Z włączonym proxy walidacja potrafi się nie powieść i zostajesz bez certyfikatu.

Nie ruszaj rekordu głównego @ ani www, jeśli stoi tam Twoja strona — dodajemy wyłącznie dwie nowe subdomeny.

4.3 Sprawdź, gdzie faktycznie wskazuje DNS

terminal · lokalnie
dig +short bi.twojadomena.pl
dig +short rozliczenia.twojadomena.pl

Oba muszą zwrócić IP Twojego serwera. Jeśli widzisz adresy zaczynające się od 104. lub 172.67., to adresy Cloudflare — proxy nadal jest włączone, wróć do punktu 4.2. Propagacja zwykle trwa poniżej minuty.

4.4 Cloudflare — tryb SSL/TLS

SSL/TLS → Overview → Configure i ustaw Full (strict).

TrybCo robiWerdykt
FlexibleCloudflare łączy się z serwerem po HTTPnigdy pętla przekierowań
FullHTTPS do serwera, bez sprawdzania certyfikatudziała, ale słabiej
Full (strict)HTTPS do serwera z weryfikacją certyfikatuto ustaw
Dlaczego nie Flexible

Coolify przekierowuje HTTP na HTTPS. W trybie Flexible Cloudflare wysyła do serwera żądanie HTTP, serwer odsyła przekierowanie na HTTPS, Cloudflare znów pyta po HTTP — i tak w kółko. Przeglądarka pokazuje ERR_TOO_MANY_REDIRECTS. To najczęstszy błąd w tej konfiguracji.

Następnie SSL/TLS → Edge Certificates:

UstawienieWartość
Always Use HTTPSON
Automatic HTTPS RewritesON
Minimum TLS VersionTLS 1.2

4.5 Otwórz porty na serwerze

Let's Encrypt potrzebuje portu 80, ruch użytkowników portu 443:

terminal · na serwerze
sudo ufw allow 80/tcp
sudo ufw allow 443/tcp
sudo ufw status

Jeśli serwer stoi u dostawcy z własnym firewallem (Hetzner, OVH, AWS), otwórz te porty również w jego panelu.

4.6 Coolify — przypisz domeny do usług

Otwórz swój zasób → Configuration. Przy usłudze Docker Compose Coolify pokazuje listę kontenerów, a każdy ma własne pole Domains. Wpisz adres razem z portem kontenera:

UsługaWartość w polu DomainsDlaczego ten port
metabasehttps://bi.twojadomena.pl:3000Metabase nasłuchuje na 3000
ingesthttps://rozliczenia.twojadomena.pl:8000uvicorn nasłuchuje na 8000
postgreszostaw pustebaza nie może być publiczna
backupzostaw pusteusługa wewnętrzna
Port po dwukropku nie jest opcjonalny

Przy stacku z wieloma usługami Coolify nie zgadnie, na który port kontenera kierować ruch. Bez :3000 i :8000 najczęściej dostaniesz 502 Bad Gateway albo trafisz na niewłaściwą usługę.

Zapisz i kliknij Deploy. Pierwsze budowanie trwa 3–5 minut.

4.7 Zweryfikuj certyfikat

terminal · lokalnie
curl -sI https://rozliczenia.twojadomena.pl/healthz | head -3

# kto wystawił certyfikat i do kiedy jest ważny
echo | openssl s_client -connect bi.twojadomena.pl:443 \
      -servername bi.twojadomena.pl 2>/dev/null \
  | openssl x509 -noout -issuer -dates

W polu issuer powinno być Let's Encrypt, a data notAfter około 90 dni w przód. Coolify odnawia certyfikat sam.

4.8 Włącz proxy Cloudflare (zalecane, ale dopiero teraz)

Skoro certyfikat działa, możesz włączyć proxy: wróć do DNS → Records i przełącz obie chmurki z szarej na pomarańczową. Tryb SSL/TLS zostaw na Full (strict) — teraz na serwerze jest prawdziwy certyfikat, więc Cloudflare go zaakceptuje.

Co zyskujeszCo musisz wiedzieć
Adres IP serwera przestaje być publicznyLimit żądania: 100 s na planie darmowym
Ochrona przed DDoS i ruchem botówLimit uploadu: 100 MB na planie darmowym
Cache i szybsze ładowanie MetabaseOdnowienie Let's Encrypt nadal działa przez proxy
Limity Cloudflare nas nie dotykają

Limit 100 sekund byłby problemem, bo przetworzenie pliku razem z dbt potrafi trwać dłużej. Dlatego worker ma tryb mode=async: odpowiada n8n natychmiast kodem 202, a n8n dopytuje o wynik przez GET /files/{sha}. Limit 100 MB też jest bez znaczenia — rozliczenie waży około 125 KB.

Po przełączeniu odczekaj minutę i sprawdź ponownie. Jeśli strona przestanie działać, wróć na szarą chmurkę i zajrzyj do kroku 11 — tabela rozwiązywania problemów ma osobną sekcję o Cloudflare.

05

Pierwszy start i weryfikacja

Migracje bazy wykonują się automatycznie przy starcie workera — nie trzeba uruchamiać ich ręcznie.

terminal · weryfikacja
# 1. Worker odpowiada i widzi bazę
curl -s https://rozliczenia.twojadomena.pl/healthz
# oczekiwane: {"status":"ok"}

# 2. Schemat został utworzony (terminal Coolify, usługa postgres)
psql -U settlements -d settlements -c "\dt core.*"
# oczekiwane: partner, period, channel, settlement, product,
#            sales_line, stock_snapshot, settlement_note

# 3. Panel ręcznego uploadu działa
# otwórz https://rozliczenia.twojadomena.pl/ (admin + ADMIN_PASSWORD)
Serwer na ARM

Stack działa natywnie na arm64: postgres:16-alpine i metabase/metabase:v0.58.31 mają obrazy arm64, a worker buduje się z python:3.12-slim — wszystkie jego zależności, łącznie z psycopg2-binary (wymaganym przez dbt), mają koła aarch64. Nic nie chodzi pod emulacją.

Jeśli healthz zwraca 503

Worker wystartował szybciej niż baza. Sprawdź logi usługi postgres i odczekaj minutę — Docker restartuje kontener sam. Jeśli błąd się utrzymuje, zwykle oznacza literówkę w POSTGRES_PASSWORD między usługami.

08

Skonfiguruj n8n Cloud

Zostajemy przy n8n Cloud — masz go opłaconego, a to o jedną usługę mniej do utrzymania, aktualizowania i backupowania na serwerze. Jedyna różnica wobec wersji self-hosted jest taka, że n8n stoi poza siecią Dockera, więc nie może sięgnąć wprost do bazy. Rozwiązaliśmy to dwoma endpointami HTTPS: workflow pyta worker zamiast pytać Postgresa.

Aspektn8n Cloud wybranen8n self-hosted
Utrzymaniezero — aktualizacje po stronie n8nTwoje aktualizacje i backupy
Dostęp do bazyprzez HTTPS i klucz APIbezpośrednio w sieci Dockera
Ryzyko utraty poświadczeńbrakutrata N8N_ENCRYPTION_KEY = konfiguracja od nowa
Zasoby serweranie zużywa~500 MB RAM

Jak działa pętla oczekiwania

Test end-to-end i wczytanie historii

Najważniejszy test: ten sam plik wgrany dwa razy musi zostać przetworzony tylko raz.

terminal · test idempotencji
export KLUCZ="<INGEST_API_KEY>"
export HOST="rozliczenia.twojadomena.pl"

# pierwsze wgranie (synchroniczne — czekamy na wynik)
curl -s -X POST https://$HOST/ingest \
     -H "X-API-Key: $KLUCZ" \
     -F "file=@Rozliczenie_2026M07_ZZMP1.xlsx" \
     -F "source=manual"
# oczekiwane: "status": "processed", "checks_failed": 0

# drugie wgranie tego samego pliku
curl -s -X POST https://$HOST/ingest \
     -H "X-API-Key: $KLUCZ" \
     -F "file=@Rozliczenie_2026M07_ZZMP1.xlsx"
# oczekiwane: "status": "duplicate" — plik pominięty

# tryb async, tak jak używa go n8n
curl -s -X POST https://$HOST/ingest \
     -H "X-API-Key: $KLUCZ" \
     -F "file=@Rozliczenie_2026M08_ZZMP1.xlsx" \
     -F "mode=async"
# oczekiwane: 202 + "file_sha256" — potem odpytaj:
curl -s https://$HOST/files/<sha> -H "X-API-Key: $KLUCZ"

Wczytanie miesięcy historycznych

Trendy miesiąc do miesiąca zaczną działać dopiero przy dwóch okresach w bazie. Jeśli masz starsze pliki, wgraj je hurtowo — dbt przeliczy modele raz, po wszystkich plikach.

terminal Coolify · usługa ingest
python -m app.cli backfill /data/archive/historia/
python -m app.cli status
Kolejność nie ma znaczenia

Pliki możesz wgrywać w dowolnej kolejności — okresy są rozpoznawane z zawartości arkusza (a gdy jej brak, z nazwy pliku), a trendy liczone są po dacie okresu, nie po kolejności wczytania.

10

Utrzymanie

Kopie zapasowe

Usługa backup wykonuje pg_dump codziennie o 3:15 do wolumenu backups, z retencją 30 dni. Prawdziwym źródłem prawdy jest jednak wolumen archive z oryginalnymi plikami Excel — z niego odtworzysz całą bazę poleceniem backfill. Oba wolumeny warto synchronizować poza serwer.

terminal · kopia i odtworzenie
# kopia na żądanie
docker compose exec postgres pg_dump -U settlements settlements \
  | gzip > kopia_$(date +%Y%m%d).sql.gz

# odtworzenie
gunzip -c kopia_20260831.sql.gz \
  | docker compose exec -T postgres psql -U settlements -d settlements

Co miesiąc — po nadejściu rozliczenia

  1. Sprawdź mail z powiadomieniem: status zakończony i zero nieudanych kontroli.
  2. Otwórz dashboard Proces — karta 4.6 pokazuje rozbieżność między arkuszami Raport i Karta. Rosnąca rozbieżność to sygnał do rozmowy z nadawcą.
  3. Przejrzyj dashboard Magazyn, kartę „Do dozamówienia” — kolumna z sugerowanym zamówieniem na 90 dni.

Aktualizacja kodu

Wypchnij zmiany do gałęzi main — Coolify przebuduje worker przy włączonym auto-deploy. Migracje bazy stosują się automatycznie i tylko raz (rejestr w tabeli ops.schema_migration), więc restart kontenera jest bezpieczny. Domeny i certyfikaty przeżywają redeploy bez zmian.

Gdy nadawca zmieni format pliku

Parser dopasowuje etykiety, nie numery wierszy — wstawienie nowego wiersza nic nie zepsuje. Zmiana nazwy pozycji lub usunięcie arkusza kończy się statusem failed i alertem, a plik zostaje nienaruszony w archiwum. Poprawka to zwykle dopisanie jednego wariantu etykiety w parser.py i ponowne wgranie pliku.

Zasada nadrzędna

Żaden błąd nie niszczy danych. Oryginalne pliki są w archiwum, ładowanie jest transakcyjne (wchodzi całość albo nic), a korekty tworzą rewizje zamiast nadpisywać poprzednie wartości. W najgorszym razie odtwarzasz całą bazę z archiwum poleceniem backfill.

Po wdrożeniu

Od tego momentu proces jest bezobsługowy: mail przychodzi, n8n Cloud go wyłapuje, worker sprawdza kwoty i ładuje dane, dbt przelicza modele, Metabase pokazuje aktualny obraz. Ręcznie dotykasz systemu tylko wtedy, gdy przyjdzie alert — albo gdy chcesz wgrać plik wcześniej niż zrobi to skrzynka.

Naturalne rozszerzenia na później: prognoza zapotrzebowania na podstawie kilku miesięcy sprzedaży, automatyczna lista zamówień w formie pliku Excel do wysłania dostawcy, oraz porównanie rentowności między kanałami, gdy dojdzie więcej niż jedno źródło sprzedaży.
